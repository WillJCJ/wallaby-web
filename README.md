## Private details (Cloudflare Access)

This project now includes a private endpoint at `/api/private/details` served by `worker.js`.
The endpoint only returns data when Cloudflare Access has authenticated the request.

### Store private values as Worker secrets

Run these commands once per environment:

```bash
wrangler secret put EVENT_ADDRESS
wrangler secret put GATE_CODE
wrangler secret put ARRIVAL_NOTES
```

### Protect routes with Access

Access policies are managed manually in the Cloudflare Zero Trust console.

**Steps:**

1. Go to [Cloudflare Zero Trust](https://one.dash.cloudflare.com/) and sign in.
2. Select your account and navigate to **Access** → **Applications**.
3. Click **Create an application** and select **Self-hosted**.
4. Fill in:
   - **Application name**: WallabyFest Private
   - **Session duration**: 24 hours (or your preference)
   - **Application domain**: Use your domain (wallabyfest.co.uk)
5. Under **Application policies**, create a new policy:
   - **Policy name**: Require Authentication
   - **Action**: Allow
   - **Rule**: Require emails ending in `@yourdomain.com` (or add specific emails)
6. Save the application.
7. In the same application, click **Policies** and configure path routing:
   - Protect `/details/*` and `/api/private/*` with the authentication policy.
8. Users trying to access those paths will see a Cloudflare Access login screen before being allowed through.

Once policies are in place, the flow is:
- User visits `/login/` (public).
- Clicks "Sign in with Cloudflare Access".
- Redirected to `/details/`, which is gated.
- After authentication, Access injects the `CF-Access-Authenticated-User-Email` header.
- `/api/private/details` endpoint checks this header and returns secrets.

### Notes

- Do not commit private values to `site/_data` or any static files.
- GitHub secrets are for CI/deploy workflows, not direct browser reads.
- Authorized users can still copy data they can view; Access controls who can access it.
